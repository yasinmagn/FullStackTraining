## 1. Set up the database

### 1.1 Get a PostgreSQL

Any of these works:

| Option | How |
|---|---|
| **Local install** | [postgresql.org/download](https://www.postgresql.org/download/) — on Windows the installer includes pgAdmin |
| **Docker** | `docker run -d --name pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16` |
| **Managed (free tiers)** | [Neon](https://neon.tech), [Supabase](https://supabase.com), [Railway](https://railway.app) |

Create a database:

```bash
createdb fullstack_training
# or:  psql -U postgres -c "CREATE DATABASE fullstack_training;"
```

### 1.2 Configure the connection

```bash
cp .env.example .env      # macOS/Linux
copy .env.example .env    # Windows
```

Set `DATABASE_URL` in `.env`:

```
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
```

If you are on a managed provider, it almost certainly requires TLS:

```
DATABASE_SSL=true
```

> ### Credentials
>
> `.env` is in `.gitignore` and must stay that way. Nothing in this repository
> contains a real connection string — `src/db.ts` reads `process.env.DATABASE_URL`
> and nothing else.
>
> Run `npm run check:secrets` from the repo root at any time; it fails if
> anything credential-shaped reaches a git-tracked file.
>

> overwrite variables that are already set — which is correct (production sets

> surprising when a shell variable silently wins over the file you just edited.
> If your changes to `.env` seem to have no effect, check `echo $DATABASE_URL`.

```bash
npm run db:setup     --workspace backend-stage-4-sql-postgres   # schema + seed
npm run queries      --workspace backend-stage-4-sql-postgres   # 12 worked queries
npm run explain      --workspace backend-stage-4-sql-postgres   # index benchmark
```

## 2. Column types: the choices that matter

Read `sql/01-schema.sql`. Four decisions are worth more than all the others.

### `timestamptz`, always. Never `timestamp`

```sql
created_at timestamptz NOT NULL DEFAULT now()
```

`timestamptz` stores an absolute instant (UTC) and converts on the way out.
`timestamp` stores wall-clock digits with no context — so `2026-03-29 01:30` is
ambiguous, unorderable across regions, and **wrong twice a year**.

This is one of the few genuinely universal rules in schema design. There is no
good reason to use `timestamp` without a time zone.

### `date` for calendar days

```sql
due_date date
```

A due date is a *day*, not an instant. Store it as a timestamp and you must
invent a time and a zone — and then it is due at a different moment for each
user.

### `numeric` for anything you do arithmetic on and care about

```sql
estimate_hours numeric(6, 2)
```

```sql
SELECT 0.1::float8 + 0.2::float8;   -- 0.30000000000000004
SELECT 0.1::numeric + 0.2::numeric; -- 0.3
```

Never `float`/`double precision` for money or billable hours.

> `pg` returns `numeric` as a **string** in JavaScript, deliberately: JS numbers
> cannot represent arbitrary precision, so parsing it would throw away the
> exactness you chose the type for. `src/db.ts` leaves it alone and explains
> why.

### `uuid` vs `serial`

| | UUID | Identity/serial |
|---|---|---|
| Generated by | Anyone, anywhere | The database only |
| Leaks row count | No | **Yes** — `/users/8134` tells a competitor a lot |
| Size | 16 bytes | 4–8 bytes |
| Insert locality | Random, fragments the index | Sequential |

For most applications UUID wins, and `gen_random_uuid()` is built in since
PostgreSQL 13. For a 10-billion-row append-only table, look at UUIDv7 (time
ordered) or an identity column.

## 3. Constraints are documentation the database enforces

A comment saying "email must contain @" is a wish. A `CHECK` is a guarantee.

```sql
CONSTRAINT users_email_shape CHECK (email LIKE '%_@_%'),

CONSTRAINT tasks_completed_at_matches_status CHECK (
  (status = 'done'  AND completed_at IS NOT NULL) OR
  (status <> 'done' AND completed_at IS NULL)
)
```

That second one is a **cross-column invariant** — exactly the kind of rule that
rots in application code, because every new code path has to remember it, and a
manual `UPDATE` from a SQL console never does.

`npm run transactions` proves all four defences fire:

```
NOT NULL               rejected, SQLSTATE 23502
FOREIGN KEY            rejected, SQLSTATE 23503
UNIQUE                 rejected, SQLSTATE 23505
CHECK (cross-column)   rejected, SQLSTATE 23514
```

### SQLSTATE codes you will handle in application code

| Code | Meaning | Typical HTTP response |
|---|---|---|
| `23502` | NOT NULL violation | 400 |
| `23503` | Foreign key violation | 400 or 409 |
| `23505` | Unique violation | **409 Conflict** |
| `23514` | CHECK violation | 400 |
| `40001` | Serialization failure | Retry |
| `40P01` | Deadlock detected | Retry |

Branch on `error.code`, never on the message. Stage 5 maps these to domain
errors.

### `ON DELETE` is a design decision, not a default

```sql
owner_id    uuid NOT NULL REFERENCES users (id) ON DELETE CASCADE,    -- projects
assignee_id uuid          REFERENCES users (id) ON DELETE SET NULL    -- tasks
```

Deleting a user deletes their projects, but **not** the tasks they were assigned
— the work survives, unassigned. The right answer differs per relationship, so
decide it each time.

| Option | Effect |
|---|---|
| `RESTRICT` / `NO ACTION` | Refuse the delete (the safe default) |
| `CASCADE` | Delete the children too (convenient, destructive) |
| `SET NULL` | Orphan the children (needs a nullable column) |

### Composite keys say what you mean

```sql
CONSTRAINT projects_name_per_owner UNIQUE (owner_id, name)   -- unique PER OWNER

PRIMARY KEY (task_id, tag_id)                                -- the pair IS the identity
```

The join table needs no surrogate id, and tagging the same task twice becomes
impossible rather than merely discouraged.

### Case-insensitive uniqueness

```sql
CREATE UNIQUE INDEX users_email_lower_key ON users (lower(email));
```

A **functional index** — the index stores the result of the expression. Now
`Ada@example.com` and `ada@example.com` cannot both exist.

## 4. Joins

Run `npm run queries` and read the output beside the SQL.

### INNER vs LEFT — the most common reporting bug

```sql
FROM users u
LEFT JOIN projects p ON p.owner_id = u.id
```

The seed data includes Katherine, who owns nothing. With `LEFT JOIN` she
appears with a count of 0; with `INNER JOIN` she vanishes from the report
entirely, and nobody notices for months.

**Rule:** if the right-hand side is optional, `LEFT JOIN`. If a count of zero
should still appear, `LEFT JOIN`.

### `FILTER` beats `CASE WHEN`

```sql
count(t.id) FILTER (WHERE t.status = 'done') AS done_count
```

Cleaner and faster than `count(CASE WHEN status = 'done' THEN 1 END)`, and it is
standard SQL.

Note `coalesce(sum(...), 0)`: **`sum()` over zero rows is NULL, not 0.**

### `WHERE` filters rows; `HAVING` filters groups

`WHERE` runs before grouping, `HAVING` after. An aggregate in `WHERE` is a
syntax error; a row condition in `HAVING` works but is slower and confusing.

### Solving N+1 in one query

Fetch 100 tasks, then loop and fetch each one's tags: **101 queries**. Each is
fast; the round trips are what kill you.

```sql
LEFT JOIN LATERAL (
  SELECT json_agg(tg.name ORDER BY tg.name) AS names
  FROM task_tags tt JOIN tags tg ON tg.id = tt.tag_id
  WHERE tt.task_id = t.id
) tags ON true
```

One round trip, already nested the way the API wants it. `LATERAL` is what lets
the subquery reference `t.id` from the outer query.

### Window functions

```sql
row_number() OVER (PARTITION BY p.id ORDER BY t.priority DESC) AS rank_in_project,
count(*)     OVER (PARTITION BY p.id)                          AS tasks_in_project
```

A window function computes across a set of rows **without collapsing them** —
each task keeps its own row while also seeing project-level context. `GROUP BY`
cannot do this.

### `RETURNING` and `ON CONFLICT`

```sql
INSERT INTO tasks (...) VALUES (...) RETURNING id, created_at;

INSERT INTO tags (name) VALUES ('backend')
ON CONFLICT (name) DO NOTHING
RETURNING id, name;
```

`RETURNING` gets the generated row back in the **same round trip**. `ON CONFLICT`
is an atomic upsert — the alternative (SELECT, then INSERT or UPDATE) has a race
between the two statements where a concurrent request inserts the same row.

## 5. Indexes

Run `npm run explain`. It builds 50,000 rows and runs the same query twice.
Here is the real output:

**Without an index:**

```
Limit  (cost=1185.83..1185.88 rows=20)  (actual time=3.526..3.530 rows=20)
  ->  Sort  (Sort Key: created_at DESC)
        ->  Seq Scan on big_tasks  (actual time=0.078..3.504 rows=33)
              Filter: ((project_id = 42) AND (status = 'todo'))
              Rows Removed by Filter: 49967
Execution Time: 3.549 ms
```

**With `(project_id, status, created_at DESC)`:**

```
Limit  (cost=0.29..80.68 rows=20)  (actual time=0.031..0.056 rows=20)
  ->  Index Scan using big_tasks_project_status_created_idx
        Index Cond: ((project_id = 42) AND (status = 'todo'))
Execution Time: 0.076 ms
```

**3.549 ms → 0.076 ms: about 46× faster.** Note `Rows Removed by Filter: 49967`
— the sequential scan read every row and threw away 99.9% of them. The sort
also disappears entirely, because the index is already in `created_at DESC`
order.

### Column order in a composite index

`(project_id, status, created_at)` serves:

- ✅ `WHERE project_id = ?`
- ✅ `WHERE project_id = ? AND status = ?`
- ✅ `WHERE project_id = ? AND status = ? ORDER BY created_at`
- ❌ `WHERE status = ?` alone

**Think of a phone book sorted by surname, then first name.** Finding everyone
called "Smith" is easy; finding everyone called "John" means reading the whole
book. The third EXPLAIN in the script demonstrates exactly this.

### PostgreSQL does not index foreign keys for you

Only `PRIMARY KEY` and `UNIQUE` get an index automatically. Every foreign key
you join or filter on needs one, and forgetting is a classic cause of a slow
`DELETE` (the database must scan the child table to check the constraint).

### Partial indexes

```sql
CREATE INDEX tasks_open_due_idx ON tasks (due_date)
  WHERE status <> 'done' AND due_date IS NOT NULL;
```

Most tasks eventually become `done`. An index over just the open ones is a
fraction of the size and stays in cache.

### Reading a plan

Read it **inside out and bottom up** — the most indented node runs first.

| Node | Means |
|---|---|
| `Seq Scan` | Reads every row. Fine on a small table; a problem on a big one |
| `Index Scan` | Walks the index, then fetches rows |
| `Index Only Scan` | Best case — the index alone answered the query |
| `Bitmap Heap Scan` | Many matches; collect locations, fetch in physical order. Usually good |
| `Nested Loop` | For each left row, probe the right. Great for few rows, disastrous for many |
| `Hash Join` | Build a hash table from one side. Usual choice for two large sets |

```
rows=1000 (actual rows=50000)
```

A large gap between **estimated** and **actual** means the planner is working
from bad statistics, and a bad plan follows. Run `ANALYZE`.

> `EXPLAIN ANALYZE` actually **runs** the query. Never use it on an
> `INSERT`/`UPDATE`/`DELETE` you do not want executed (or wrap it in a
> transaction and roll back).

## 6. Transactions

Run `npm run transactions`.

### Atomicity

```
tasks before: 7
  inserted a task inside the transaction...
  second insert failed: violates check constraint "tasks_completed_at_matches_status"
tasks after:  7  <- unchanged. Both inserts were rolled back.
```

All of it, or none of it.

### Use a dedicated client — this one causes real corruption

```ts
// ✗ BROKEN. These may run on DIFFERENT pooled connections.
await pool.query('BEGIN');
await pool.query('UPDATE ...');
await pool.query('COMMIT');

// ✓
const client = await pool.connect();
try {
  await client.query('BEGIN');
  ...
  await client.query('COMMIT');
} catch (e) {
  await client.query('ROLLBACK');
  throw e;
} finally {
  client.release();     // ← non-negotiable
}
```

A transaction is state on **one connection**. The broken version leaves an empty
transaction open on one connection and an auto-committed write on another. It
appears to work in development, where the pool has one idle connection, and
corrupts data under load.

**The `finally` matters just as much.** A client that is never released is gone
from the pool forever. Leak `max` of them and the app stops responding with no
error at all — just requests waiting for a connection that never comes back.
This is one of the most common Node/PostgreSQL outages there is.

### The lost update

```ts
const task = await db.query('SELECT estimate_hours FROM tasks WHERE id = $1');
const next = task.estimate_hours + 1;                 // ← in JavaScript
await db.query('UPDATE tasks SET estimate_hours = $1 ...', [next]);
```

Two requests read 6, both compute 7, both write 7. **One increment is lost,
silently, with no error anywhere.**

Three fixes, in order of preference:

1. **Do the arithmetic in SQL** — one atomic statement, no lock needed:
   ```sql
   UPDATE tasks SET estimate_hours = estimate_hours + 1 WHERE id = $1
   ```
2. **`SELECT ... FOR UPDATE`** — lock the row for the rest of the transaction.
   For when the new value cannot be expressed in one statement.
3. **Optimistic locking** — add a `version` column,
   `UPDATE ... WHERE id = $1 AND version = $2`, and check `rowCount`. Zero
   means someone else won: retry, or return 409.

### Isolation levels

| Level | Dirty read | Non-repeatable read | Phantom read |
|---|---|---|---|
| **READ COMMITTED** *(default)* | no | **possible** | **possible** |
| REPEATABLE READ | no | no | no\* |
| SERIALIZABLE | no | no | no |

\* PostgreSQL's `REPEATABLE READ` is stronger than the standard requires and
also prevents phantoms.

The script demonstrates it: inside a `REPEATABLE READ` transaction, two
identical counts both return 7 even though another connection committed an
insert in between. Outside, the count is 8.

**Stronger isolation is not free.** `REPEATABLE READ` and `SERIALIZABLE` can
fail with SQLSTATE `40001`, and your application **must** retry the whole
transaction. Use the default until you have a specific reason not to.

## 7. Triggers and views

```sql
CREATE TRIGGER tasks_set_updated_at BEFORE UPDATE ON tasks
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

Maintaining `updated_at` in application code means every code path must
remember — and the one that forgets is always the one you debug at 2am. Manual
`UPDATE`s from a console never remember at all.

A **view** is a stored query, not a stored table. `project_summary` keeps the
definition of "the numbers everyone quotes" in one place, so the dashboard and
the report cannot disagree.

> Use triggers sparingly. They are invisible from the application, which is
> exactly why `updated_at` is a good use and "send an email on insert" is not.

## 8. Exercises

Work in `psql`, or add files to `sql/`.

### Exercise 1 — Overdue tasks
Find tasks past their due date, not done, with the assignee's name and days
overdue. Sort worst first.
*`current_date - due_date` gives an integer number of days.*

### Exercise 2 — Tag co-occurrence
Which pairs of tags appear on the same task most often?
*Self-join `task_tags` with `tt1.tag_id < tt2.tag_id` — that inequality is what
stops you counting each pair twice and pairing a tag with itself.*

### Exercise 3 — A recursive CTE
Add `parent_task_id uuid REFERENCES tasks(id)` and write a `WITH RECURSIVE`
query that returns a whole subtree with its depth.
*This is how you query any tree in SQL: categories, org charts, threads.*

### Exercise 4 — Prove an index earns its place
Add `CREATE INDEX ON tasks (status)` to the 50,000-row table and `EXPLAIN` a
`WHERE status = 'todo'` query. It matches a third of the table — does the
planner use the index? Why not?
*The answer is the most important thing to understand about indexes.*

### Exercise 5 — Watch a lock block
Open two `psql` sessions. In the first, `BEGIN; SELECT ... FOR UPDATE;` a row.
In the second, try to `UPDATE` the same row. Watch it hang. `COMMIT` the first
and watch the second complete.
*Then look at `pg_locks` and `pg_stat_activity` while it is blocked — that is
how you diagnose a stuck production database.*

### Exercise 6 — Break a constraint on purpose
Try to violate every constraint in the schema. Note the SQLSTATE for each.
Those codes are what Stage 5 maps to HTTP responses.
